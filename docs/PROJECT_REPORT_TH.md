### บทคัดย่อ

โครงงานนี้พัฒนาระบบถามตอบจากเอกสารโรคไม่ติดต่อเรื้อรัง หรือ NCD ภาษาไทย เพื่อช่วยผู้ใช้ค้นคำแนะนำและกลับไปตรวจข้อความอ้างอิงได้สะดวก ระบบนำ corpus และ hybrid retrieval จากโครงงาน Thai NCD Guideline QA มาใช้ต่อ แล้วเพิ่ม Gemma ผ่าน class proxy, native tool calling, agent loop และการตรวจคำตอบกับหลักฐาน หน้าจอแสดงคำตอบพร้อมเอกสาร ฉบับพิมพ์ เลขหน้า และข้อความที่ใช้อ้างอิง

ผล frozen retrieval test พบว่า hybrid retrieval ให้ Strict Recall@5 เท่ากับ 0.8846 สูงกว่า dense baseline ที่ 0.8077 การประเมิน v32 ใช้โค้ดปัจจุบันและ cache ใหม่ ได้สาระครบ 24/25 ข้อใน dev ชุดเดิม และได้ผลสำเร็จ 28/30 ข้อใน extra-dev เมื่อรวมการงดตอบที่ถูกต้อง ยังพบปัญหา structured output ที่ทำให้งดตอบเกินจำเป็น และมีบันทึกบริการขัดข้องในรอบ v31 การตรวจสาระทำโดย coding agent บนชุดที่เคยใช้ปรับระบบ ไม่ใช่การยืนยันทางคลินิก

### 1. ปัญหาและวัตถุประสงค์

เอกสารแนวทางมีหลายฉบับและมักอธิบายข้อแนะนำผ่านตารางหรือเงื่อนไขเฉพาะกลุ่ม การค้นพบข้อความที่มีคำตรงกันจึงยังไม่เพียงพอ ผู้ใช้ต้องรู้ด้วยว่าคำแนะนำนั้นใช้กับกลุ่มใดและอยู่ในบริบทใด ระบบนี้มุ่งช่วยผู้ใช้ทั่วไปและนักศึกษาที่ต้องการอ่านแนวทาง โดยลดเวลาค้นหาและทำให้ที่มาของคำตอบตรวจสอบได้

วัตถุประสงค์คือพัฒนาแอปที่ค้นหลักฐานก่อนตอบ เรียก tool ได้ภายในขอบเขตที่กำหนด และประเมินผลเทียบ baseline อย่างทำซ้ำได้ ขอบเขตของระบบคือการอ่านเอกสาร ไม่รวมการวินิจฉัย การสั่งยา หรือการจัดแผนรักษาเฉพาะบุคคล เมื่อข้อมูลไม่พอ ระบบควรงดตอบหรือขอรายละเอียดเพิ่มตามลักษณะคำถาม

## 2. สถาปัตยกรรมและการออกแบบระบบ

![ภาพที่ 1 สถาปัตยกรรมของระบบและเส้นทางตอบคำถาม](diagrams/architecture.svg)

ระบบรับคำถามผ่านหน้าเว็บภาษาไทยและ FastAPI จากนั้นใช้ OpenAI SDK เรียกโมเดล gemma-4-E4B-it ที่ https://llm.nat-d.uk/v1 โดยอ่าน OPENAI_API_KEY และ OPENAI_BASE_URL จาก environment คำถามในขอบเขตต้องเริ่มด้วย native search_docs โค้ดตรวจชื่อ tool และ arguments ก่อนค้น และส่งผลกลับพร้อม tool_call_id ที่ตรงกัน คำทักทายล้วนตอบด้วยข้อความระบุขอบเขตโดยไม่เรียกโมเดล

เมื่อได้หลักฐาน ระบบใช้ source bound reader หากตรวจความสัมพันธ์ในข้อความได้ครบ มิฉะนั้นให้ Gemma เสนอคำตอบและตรวจอีกครั้งกับหลักฐาน ทุกเส้นทางต้องผ่านการตรวจ schema และ citation รวมถึงเงื่อนไขเฉพาะที่เกี่ยวข้อง กล่อง Grounding checks ในภาพรวมทั้งสองเส้นทางไว้ด้วยกัน ส่วน gold ถูกใช้เฉพาะการประเมินผล ไม่มีการอ่าน reference answer ใน serving layer

Configuration ที่ใช้ประเมินจำกัด 6 model rounds รวมรอบตรวจคำตอบ ค้นได้ไม่เกิน 3 ครั้ง top_k ไม่เกิน 8 และ context ไม่เกิน 18,000 ตัวอักษร กำหนด request timeout 45 วินาทีและเวลารวม 150 วินาที จึงหยุดได้เมื่อคำตอบผ่านเกณฑ์ หลักฐานไม่พอ หรือใช้ budget ครบ โดยไม่เปิดให้โมเดลเรียก shell หรือเลือกอ่านไฟล์ได้เอง

## 3. ข้อมูล เทคนิค และส่วนที่พัฒนาเพิ่ม

### 3.1 ชุดข้อมูลและการนำงานเดิมมาใช้

ใช้ snapshot normalized-v12 จาก Thai NCD Guideline QA โดยคัดลอกข้อมูลและ retrieval modules มาไว้ใน repository ของโครงงานนี้ ไฟล์ต้นทางและ gold ไม่ถูกแก้ไข การนำเข้าบันทึก SHA-256 เพื่อให้ตรวจสอบย้อนกลับได้ Gold มี 162 ข้อจากไฟล์คำถามทั้งหมด 177 แถว ส่วน rejected 15 ข้อไม่นำมาประเมิน

ตารางที่ 1 ข้อมูลหลักที่ใช้ในระบบ

| รายการ | รายละเอียด |
| --- | --- |
| Corpus | 66 เอกสารที่มี chunks ใน snapshot normalized-v12 |
| Chunks และ index | Child 23,819 ชิ้น Parent 4,347 ชิ้น และ dense vectors ขนาด 1,024 มิติ |
| Gold | Dev 106 ข้อ และ test 56 ข้อ โดย test ตอบได้ 52 ข้อ |
| ชุดประเมินคำตอบ | Dev ชุดเดิม 30 ข้อ และ extra-dev อีก 30 ข้อที่ไม่ซ้ำกัน |

### 3.2 เหตุผลของการเลือก retrieval

นำ variant B ซึ่งรวม dense search ของ bge-m3 กับ BM25 มาใช้เป็นแกนหลัก Dense search ช่วยค้นความหมาย ส่วน BM25 ช่วยรักษาคำเฉพาะ ชื่อยา และตัวเลข ใช้ child 128 tokens และ parent 512 tokens, BM25 char3 ที่ k1 เท่ากับ 2.18 และ b เท่ากับ 0.86 แล้วปรับคะแนนด้วย min-max ก่อน convex fusion ที่ alpha เท่ากับ 0.6 และ candidate pool 100 ค่าเหล่านี้สืบทอดจาก frozen configuration เดิม ไม่ได้ปรับจากผล test ในงานนี้

### 3.3 วิธีลดคำตอบผิดและการงดตอบเกินจำเป็น

ส่วนที่เพิ่มคือการต่อข้อความข้างเคียง การเลือก short passage และเรียงด้วย bge-reranker-v2-m3 รวมถึง exact lexical admission เฉพาะคำถามความสัมพันธ์ของ field ที่ตรวจตรงข้อความได้ สำหรับตาราง ใช้ PyMuPDF อ่านตำแหน่งเซลล์และหัวคอลัมน์ แล้วให้ระบบประกอบค่าที่เลือกจากเซลล์จริง แทนการให้โมเดลเขียนตัวเลขใหม่ทั้งหมด

ด้านคำตอบ ใช้ claim และ passage IDs เพื่อผูกข้อความกับ source ตรวจ quote แบบตรงข้อความ และตรวจความครบของหน่วย ตัวหาร ประชากร และเงื่อนไข คำถามบางกลุ่มมี source bound reader ที่อ่านค่าจากหลักฐานโดยตรง ไม่ใช้ qid หรือเฉลยกำหนดคำตอบ หากเงื่อนไขไม่ครบจะกลับสู่ Gemma และ reviewer การซ่อมรูปแบบกับการซ่อมเนื้อหาแยกกันและใช้ budget เดิม เทคนิคเหล่านี้ลดข้อผิดพลาดที่พบระหว่างพัฒนา แต่กฎยังอาจไม่ครอบคลุมสำนวนใหม่

## 4. วิธีประเมินและผลการค้นหลักฐาน

### 4.1 แยกการวัด retrieval ออกจากการวัดคำตอบ

การประเมิน retrieval ใช้ saved ranked hits ของระบบ A, B และ C เทียบ gold เดิมและคำนวณ metric ใหม่ จึงเป็นการ replay ผลค้นที่ตรึงไว้ ไม่ใช่การรัน retrieval ใหม่ ส่วนการประเมินคำตอบใช้คำถาม dev ที่ล็อกก่อนรัน โดยส่งให้ Gemma เฉพาะคำถามและหลักฐาน แล้วใช้ gold ตรวจผลภายหลัง แผนบันทึก qids, model, parameters และ hashes ของ implementation เพื่อระบุว่าแต่ละผลมาจากระบบรุ่นใด

### 4.2 Baseline และผลที่วัดได้

กำหนด A dense parent-child เป็น baseline Strict relevance ตรวจความตรงของ edition ช่วงหน้า และ quote ตาม protocol เดิม Recall@5 วัดสัดส่วนหลักฐานอ้างอิงที่พบในห้าอันดับแรก ส่วน MRR@10 วัดอันดับของผลที่เกี่ยวข้องรายการแรก ค่าเฉลี่ยใช้เฉพาะ test ที่ตอบได้ 52 ข้อ

ตารางที่ 2 ผล frozen retrieval test

| ระบบ | Recall@5 | MRR@10 |
| --- | --- | --- |
| A dense baseline | 0.8077 | 0.6181 |
| B hybrid ที่นำมาใช้ | 0.8846 | 0.7374 |
| C hybrid และ reranker จากงานเดิม | 0.9135 | 0.7706 |

B เพิ่ม Recall@5 เท่ากับ 0.0769 หรือ 7.69 percentage points และเพิ่ม MRR@10 เท่ากับ 0.1193 เมื่อเทียบ A ตัวเลขนี้สนับสนุนการเลือก hybrid มากกว่า dense เพียงอย่างเดียว แอปยังเพิ่ม passage reranking ซึ่งไม่ใช่ pipeline C เดิม จึงไม่ใช้คะแนน C อ้างเป็นผลของแอปหรือเป็นความถูกต้องของคำตอบ

### 4.3 ความครบถ้วนตามขอบเขตโครงงาน

ตารางที่ 3 ความเชื่อมโยงกับ capability families ของโจทย์

| Family | หลักฐานในโครงงาน |
| --- | --- |
| 1 Structured output | Pydantic schemas และ bounded format repair |
| 2 Retrieval และ RAG | Hybrid retrieval พร้อม source IDs และ citations |

## 5. ผลการประเมินคำตอบและการวิเคราะห์

### 5.1 Dev ชุดเดิม 30 ข้อ

ชุดเดิมประกอบด้วยคำถาม condition, fact, multi_page, number_unit, table และ unanswerable อย่างละ 5 ข้อ มีข้อที่ตอบได้ 25 ข้อและควรงดตอบ 5 ข้อ การตรวจสาระทำโดย coding agent เทียบคำตอบกับ gold และหลักฐาน ไม่ใช่ผู้เชี่ยวชาญอิสระ

ตารางที่ 4 ผลคำตอบในกลุ่ม answerable 25 ข้อ

| รุ่น | สาระครบ | ผิดหรือไม่ครบ | งดเกิน | Citation hit | Char. F1 |
| --- | --- | --- | --- | --- | --- |
| v13 | 14 | 9 | 2 | 0.5600 | 0.2805 |
| v27 | 24 | 1 | 0 | 0.7200 | 0.4265 |
| v30 | 25 | 0 | 0 | 0.7200 | 0.4453 |
| v31 | 24 | 0 | 1 | 0.7200 | 0.4439 |
| v32 | 24 | 0 | 1 | 0.7200 | 0.4439 |

v32 ได้สาระครบ 24/25 ข้อ เพิ่มจาก v13 จำนวน 10 ข้อ แต่ลดลง 1 ข้อเมื่อเทียบ v30 และงดตอบตรง label 5/5 ข้อ Decision accuracy 0.9667 วัดการเลือกตอบหรืองด ส่วน Citation hit ตรวจ primary evidence และ Character F1 วัด text overlap

### 6.2 ผลทดสอบซอฟต์แวร์

ตรวจซ้ำวันที่ 20 ตุลาคม 2569 ผ่าน 176 tests ไม่มี failure, error หรือ skipped มี Starlette deprecation warning หนึ่งรายการ Tests ครอบคลุม tool protocol, schema, citations, timeout, retry, scope, ตารางและ API รวมถึง guard ใหม่ที่ปฏิเสธโค้ด ข้อมูล config หรือคำตอบ resume ซึ่งไม่ตรงแผน รันนอก Windows sandbox เพื่อให้ TestClient สร้าง socketpair ได้

Unit และ API tests ใช้ fake model กับ retriever จึงอ่านแยกจากผลคำตอบจริง การตรวจไฟล์ต้นทางที่ใช้ 48 ไฟล์และ PDF ต้นทาง 33 ไฟล์พบ hash เดิม Gold และข้อมูล release 34 ไฟล์ไม่เปลี่ยน รอบนี้แก้ evaluation harness โดยคง prompt และวิธีตอบเดิมไว้

### 6.3 ข้อจำกัดของหลักฐานการประเมิน

ทั้งสองชุดคำตอบถูกใช้ปรับระบบแล้ว การคัด quote และ source bound reader ช่วยลดการแต่งเนื้อหาแต่ยังจำกัดตามรูปแบบภาษาที่รองรับ Corpus อาจไม่ครอบคลุมแนวทางทุกฉบับหรือข้อมูลปัจจุบัน ระบบยังต้องทดสอบคำถามใหม่และให้ผู้เชี่ยวชาญอ่านคำตอบก่อนนำผลไปกล่าวอ้างด้านคลินิก นอกจากนี้ test ของ retrieval เป็น snapshot จากงานเดิมซึ่งทีมเคยเห็นผลแล้ว

## 7. การทำซ้ำ ข้อสรุป และแนวทางพัฒนา

### 7.1 สิ่งที่ผู้ตรวจสามารถทำซ้ำได้

Public repository มีโค้ด คำสั่งติดตั้ง evaluation scripts และผล aggregate ชุด data-v12 release มีข้อมูลที่ extract แล้ว index, gold, frozen ranked hits และ table context รวม 34 ไฟล์ สคริปต์ public_data.py fetch ตรวจ SHA-256 ก่อนใช้งาน จึงไม่ต้องเข้าถึง source repository ในเครื่องของผู้จัดทำ ผู้จัดทำยืนยันสิทธิ์เผยแพร่ข้อมูล ส่วนเอกสารขอบเขตการอนุญาตไม่ได้แนบใน repository

ผู้ตรวจติดตั้งตาม README แล้วใช้ evaluate plan หรือ evaluate agent พร้อม --version v32 --suite both แผนใหม่ตรวจโค้ด ข้อมูล config และค่ารันก่อนเริ่มและหลังจบ ผล v30 เก็บแยกใน history เพราะ llm.py และ config.py เปลี่ยนหลัง lock เดิม หากแก้โค้ดอีกต้องเลือกเลขรุ่นใหม่ ผลคำตอบดิบและ cache ไม่เผยแพร่ การเริ่มจาก clean clone ต้องมี class proxy key ส่วนการเรียกซ้ำในเครื่องเดิมจะ resume จึงต้องอ่านจำนวน API calls ประกอบ

วันที่ 20 ตุลาคม 2569 ตรวจ clean clone จาก GitHub ตรวจข้อมูล release 34 ไฟล์ replay retrieval 6 runs และแผน v32 ทั้งสองชุดผ่าน หลังแก้ LF/CRLF ใน Git สามไฟล์ให้ตรงกับ raw bytes ที่ประเมิน โดยไม่เปลี่ยนเนื้อหาหรือ gold การตรวจใช้ Python environment เดิม เดโม HTTPS ใช้ Cloudflare Quick Tunnel จึงต้องเปิดเครื่องและ tunnel ค้างไว้ URL เปลี่ยนได้ ส่วน Dockerfile ยังไม่ยืนยันการรันทั้งระบบบน Linux

### 7.2 ข้อสรุปและงานต่อไป

โครงงานมีเส้นทางตั้งแต่รับคำถามจนแสดงหลักฐาน พร้อม baseline และผลที่ตรวจย้อนกลับได้ แผนใหม่แก้ความไม่ตรงกันระหว่างโค้ดกับ evaluation และการเรียกใหม่เปิดเผยข้อจำกัดที่ cache เดิมไม่แสดง งานต่อไปควรปรับ structured output และการซ่อมตาม schema โดยคงการตรวจตาราง แล้วทดสอบชุดใหม่ ทำ blind review และ ablation เพื่อวัดผลของแต่ละส่วน
